# Общий склад Kaspi + Flip — согласованные решения (2026-11-28)

Таблица: GRANTS BOOK (1dLU5KOi3WBLy3uNEiqGv5rf9ka0OwcEw_RjhDQW3H1E)

## Источник остатка
- Общий физический остаток = «СКЛАД_НАЛИЧИЕ» F «Доступно для продажи» (C — факт, вводит владелец).
- «Прайс KASPI» P НЕ использовать (это виртуальные 30/35 для перепродажи WB, Kaspi-предзаказ).

## Flip XML
- `<offers><offer><code/><name/><price/><count/><barcode/></offer></offers>`, UTF-8; barcode только если есть; offer с count=0 не удалять.
- Связанный товар («Flip map» Активен=TRUE и SKU заполнен): count = max(0, F − FLIP_SAFETY_BUFFER), SKU нет в СКЛАД_НАЛИЧИЕ → 0; цена = «Flip map» D (Цена Flip); пусто → count=0.
- Несвязанный: count = «Прайс Flip» C, price = «Прайс Flip» I; нет цены → count=0.
- Строить из «Прайс Flip» (точное совпадение кода), все 231 код. «flip для добавления» не трогать.
- FLIP_SAFETY_BUFFER = 1 по умолчанию. Flip забирает раз в час. Эндпоинт Vercel /api/flip рядом с /api/kaspi.

## Заказы Flip
- KL_FLIP_ORDERS_RUN каждые 5 мин, LockService, ключ `flip|preorderId`, списание при первом появлении.
- Первый запуск: текущие заказы только REGISTER_ONLY, без списания.
- Связанный товар → списание через существующий механизм F (после изучения кода). Несвязанный → «Прайс Flip» C (только колонка C), тот же ключ.
- statusGoods раз в час: отмена/возврат → вернуть туда же, откуда списали (идемпотентно); выполнен → закрыть.
- Минус не допускать: 0 + «Flip ошибки» CONFLICT + письмо на KL_NOTIFY_EMAIL (через существующий klNotifySend_; Telegram не используем, Notify.gs не меняем).
- Возвраты — только ручным подтверждением через _KASPI_RETURN_TASKS / KL_CONFIRM_RETURN_RESTOCK, как у Kaspi.
- doGet: разрешено добавить ветку `?feed=flip` (без параметра — без изменений).

## Статусы Flip (statusGoods status_code) → действие с остатком
| Код | Значение | Действие |
|---|---|---|
| 1 | Ожидает подтверждения поставщиком | ждать (резерв держится) |
| 2 | Ожидает отправки поставщиком (в поставке wait) | ждать (резерв держится) |
| 3 | В пути от поставщика | ждать; фиксируем отгрузку (SHIP, остаток не меняется) |
| 4 | Ждет прихода | ждать; отгрузка (как 3) |
| 5 | Доставляется клиенту | закрыть, остаток не трогать |
| 6 | Выполнен | закрыть, остаток не трогать |
| 7 | Свободен на складе Flip | закрыть, остаток не трогать |
| 8 | Отменен покупателем | +1 ТОЛЬКО если не отгружали (в ledger нет SHIP и в истории нет 3+); иначе закрыть без возврата |
| 9 | Отменен поставщиком | +1 (книга не уезжала) |
| 10 | Возвращен поставщику | +1 только ручным подтверждением (_KASPI_RETURN_TASKS) |
| 11 | Возвращается поставщику | ждать |
| 12 | Возвращается от клиента | ждать |
| — | нет status_code | статус неизвестен, перезапросить позже |
- Код 9 при уже зафиксированной отгрузке (противоречие) → не возвращать, «Flip ошибки» STATUS на ручной разбор.
- Строки FLIP_REGISTERED (первый запуск) остаток не меняют никогда; по 5–10 только закрываются.
- Код не найден → «Flip ошибки» UNMAPPED. POST /orders/cancel не вызывать.
- FLIP_DRY_RUN=TRUE до подтверждения владельца. FLIP_API_KEY только в Script Properties.

## Перенос «Flip перенос» → «СКЛАД_НАЛИЧИЕ» (подтверждено, пп. 1–6)
1. Только строки Перенести=TRUE + Факт на полке + SKU.
2. SKU есть → C := факт (замена; факт = всё на полке), «Дата подсчёта» = сегодня.
3. SKU нет → новая строка (SKU, C=факт, дата), формулы B/I как у соседей.
4. Несколько кодов Flip на SKU → один факт; разные факты → ошибка, не переносить.
5. Успех → «Flip map» Активен=TRUE для этого кода, статус «перенесено <дата>, C X→Y».
6. Повтор не трогает перенесённые.
- Сначала dry-run, показать, запуск только по «ок».
- СТОП-условие: если по коду смена «Даты подсчёта» меняет учёт уже принятых Kaspi-заказов не так, как ожидается — сначала сообщить, не переносить.
- СРАБОТАЛО (см. FLIP_PLAN.md §1): из C вычитается и резерв, открытый на момент D.
  Ждём выбор владельца: А — факт включает отложенные под заказы (C := факт),
  Б — отложенные лежат отдельно (C := факт + E). До выбора перенос заблокирован.
